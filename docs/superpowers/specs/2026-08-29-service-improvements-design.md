# Service improvements: надёжность, пагинация/фильтры, редизайн UI

## Problem

Обзор сервиса выявил две группы проблем.

**Надёжность.** Ручной запуск дайджеста выполняется синхронно внутри цикла планировщика и блокирует его до 50 минут; при переполнении канала триггеров запуск молча теряется, хотя API уже ответил «queued». Запуски, прерванные рестартом сервера, навсегда остаются в статусе `processing`. Сбой отправки письма только логируется — пользователь считает, что дайджест ушёл. Картинки скачиваются без лимита размера и без защиты от SSRF (URL приходят из ответа агента). `/runs/{id}/view` доступен без авторизации, защищён только непредсказуемостью UUID. История растёт без ограничений (в каждой записи полный HTML), протухшие refresh-токены копятся, логин не защищён от перебора.

**UX.** В «Дайджестах» и «Истории» нет пагинации — «История» рендерит до 500 записей разом. Нет фильтра по дайджесту и статусу. Статусы `processing` и `empty` выглядят как ошибки (красный бейдж). Подтверждения и уведомления — через `alert()`/`confirm()`. Нет тёмной темы, иконок; внешний вид требует модернизации.

## Goal

- Планировщик не блокируется ручными запусками; потерянных «в никуда» запусков нет; зависших `processing` нет.
- Сбой почты виден в «Истории»; отправка ретраится.
- Скачивание картинок ограничено по размеру и защищено от SSRF; просмотр запуска — по короткоживущей подписанной ссылке; логин защищён от перебора; история и refresh-токены чистятся.
- Оба раздела списков постранично (`page`/`per_page`), «История» фильтруется по дайджесту и статусу.
- Тёмная тема с трёхпозиционным переключателем (system → light → dark).
- Редизайн в строгом минимализме (выбран на макетах: светлая — «вариант C», тёмная — slate «вариант B»), иконки, тосты, модалки подтверждения, автообновление «Истории» во время обработки.

## Non-goals

- Мультиинстансный деплой: блокировка «дайджест уже выполняется» остаётся in-memory, ретеншен и sweep рассчитаны на один экземпляр.
- Graceful-ожидание незавершённых запусков при shutdown — запуск длится до 50 минут, ждать бессмысленно; случай покрывается сбросом `processing` на старте.
- Изменение `ON DELETE CASCADE`: история удаляется вместе с дайджестом, UI предупреждает об этом в подтверждении удаления.
- Keyset-пагинация: выбраны классические страницы; `LIMIT/OFFSET` при сотнях–тысячах строк достаточно.
- Редизайн HTML-шаблона письма — меняется только веб-приложение.
- Роли пользователей, аудит действий, квоты на размер хранилища картинок.

## Design

### 1. API

Списковые эндпоинты переходят на конверт:

```json
{"items": [...], "total": 142}
```

- `GET /api/digests?page=1&per_page=20` — сортировка `created_at DESC` (как сейчас).
- `GET /api/runs?page=1&per_page=20&digest_id=<uuid>&status=<ok|error|empty|processing>` — сортировка `processed_at DESC`; фильтры опциональны и комбинируются (`WHERE` собирается динамически).
- Валидация: `page ≥ 1`, `1 ≤ per_page ≤ 100` (дефолт 20), `status` по whitelist, `digest_id` — валидный UUID; иначе 400.
- Элементы `/api/runs` дополняются `materials_count` (подзапрос `COUNT(*)` по `digest_materials`) и `mail_status`/`mail_error`.
- `GET /api/digests/options` → `[{"id":..., "name":...}]` — источник выпадающего фильтра, без пагинации, сортировка по имени.
- `POST /api/digests/{id}/run`: если очередь триггеров переполнена — 503 `{"error":"очередь запусков переполнена"}` вместо ложного 202.
- `GET /api/runs/{id}/view-link` (под авторизацией) → `{"url":"/runs/<id>/view?exp=<unix>&sig=<hmac>"}`, TTL 15 минут.

Обратная совместимость формата списков не требуется: фронт — единственный потребитель API и обновляется вместе с бэком.

### 2. БД (миграция 005)

```sql
ALTER TABLE digest_runs
    ADD COLUMN mail_status TEXT NOT NULL DEFAULT '',
    ADD COLUMN mail_error  TEXT NOT NULL DEFAULT '';
ALTER TABLE settings
    ADD COLUMN keep_runs_days INT NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS idx_digest_runs_processed ON digest_runs(processed_at DESC);
CREATE INDEX IF NOT EXISTS idx_digest_runs_status ON digest_runs(status, processed_at DESC);
```

`mail_status`: `''` (не применимо / старые записи), `sent`, `failed`, `skipped` (нет получателей или SMTP не настроен). `keep_runs_days = 0` — хранить вечно.

### 3. Надёжность

**3.1. Асинхронный ручной запуск.** В `scheduler.loop` ветка `case id := <-s.trigger:` вызывает `go s.runOne(ctx, id, false)` — как это уже делает `tick` для плановых запусков. Защита от параллельного запуска одного дайджеста остаётся на `processor.tryLock`.

**3.2. Честная очередь.** `Trigger(id string) bool`: `true` — принято, `false` — канал полон. Хендлер `triggerDigest` транслирует `false` в 503, UI показывает тост с ошибкой. В `createDigest` (ветка «включенный дайджест запускается сразу») результат только логируется: создание не должно падать из-за очереди, а у нового дайджеста `next_run_at IS NULL` — ближайший тик планировщика запустит его сам.

**3.3. Сброс зависших запусков.** При старте сервера (в `main`, до `scheduler.Start`):

```sql
UPDATE digest_runs
SET status='error', error='прерван перезапуском сервера', processed_at=now()
WHERE status='processing';
```

**3.4. Видимость почты.** `sendMail` возвращает результат; до 3 попыток с паузами 5 с и 30 с между ними. Итог пишется в `digest_runs.mail_status`/`mail_error` отдельным `UPDATE` (новый метод `repo.SetRunMail`). Ретраи выполняются в горутине запуска — на планировщик не влияют.

**3.5. Лимиты и SSRF-защита картинок** (`internal/images`):

- скачивание картинки — через `io.LimitReader` на 10 МБ; при превышении файл отбрасывается;
- принимаются только ответы с `Content-Type: image/*`;
- общий `http.Client` для OG-страниц и картинок получает кастомный `DialContext`, который резолвит адрес и отклоняет соединение, если IP loopback / private / link-local / multicast / unspecified (проверка на уровне соединения покрывает и редиректы);
- допускаются только схемы `http`/`https`.

**3.6. Подписанные ссылки просмотра.** Подпись `sig = hex(HMAC-SHA256(JWT_SECRET, runID + "|" + exp))`, `exp` — unix-время истечения (now + 15 мин). `GET /runs/{id}/view` проверяет подпись и срок; иначе 404 (не раскрываем существование записи). Фронт перед открытием вкладки запрашивает `/api/runs/{id}/view-link` и открывает полученный URL. `/images/` остаётся публичным — на него ссылаются письма.

**3.7. Ретеншен и чистка.** В `scheduler.tick` раз в сутки (отметка последней чистки в памяти планировщика):

1. если `keep_runs_days > 0`: выбрать `id` запусков с `processed_at < now() - keep_runs_days * '1 day'`, удалить записи (материалы каскадом) и каталоги `storage/images/<run_id>`;
2. `DELETE FROM refresh_tokens WHERE expires_at < now()`.

Настройка «Хранить историю, дней (0 — вечно)» добавляется в UI раздела «Настройки → Обработка».

**3.8. Rate-limit логина.** In-memory-лимитер в `internal/auth`: ключ — `IP + "|" + email`; после 5 неудач подряд блокировка на 60 с, каждая следующая неудача удваивает время до максимума 15 мин; успешный вход сбрасывает счётчик. Пока блокировка активна, `login` отвечает 429 без обращения к БД. Просроченные записи лимитера периодически вычищаются (лениво, при обращениях).

### 4. Фронтенд

**4.1. Структура.** `app.js` разбивается на ES-модули (без сборщика, `<script type="module" src="/js/app.js">`):

```text
web/
  index.html          — каркас, SVG-спрайт иконок
  styles.css          — токены и стили (светлая + тёмная)
  js/
    app.js            — boot, роутер, шапка
    api.js            — fetch-обёртка, токены, refresh
    theme.js          — трёхпозиционная тема
    ui.js             — тосты, confirm-модалка, пагинатор, хелпер иконок, esc()
    views/digests.js
    views/runs.js
    views/settings.js
```

**4.2. Иконки.** Инлайн SVG-спрайт в `index.html` (`<symbol>` + `<use href="#i-...">`, stroke-стиль, 16–18 px): `i-digest` (сетка), `i-history` (часы), `i-settings` (шестерёнка), `i-play`, `i-edit`, `i-trash`, `i-plus`, `i-logout`, `i-mail`, `i-mail-x`, `i-filter`, `i-chevron-left`, `i-chevron-right`, `i-external`, `i-sun`, `i-moon`, `i-monitor`, `i-check`, `i-x`.

**4.3. Тема.** `theme.js` хранит в `localStorage('theme')` одно из `system|light|dark` (дефолт `system`) и выставляет `data-theme` на `<html>` (для `system` — атрибут снимается). Кнопка в шапке циклит состояния и показывает иконку текущего (`i-monitor`/`i-sun`/`i-moon`). Инлайн-скрипт в `<head>` применяет сохранённую тему до загрузки CSS — без вспышки светлого фона.

CSS: полный набор токенов в `:root` (светлая палитра); тёмные значения — в `@media (prefers-color-scheme: dark)` под guard `:root:not([data-theme="light"])` и продублированы в `:root[data-theme="dark"]`.

**4.4. Палитры.**

| Токен | Светлая (стиль C) | Тёмная (slate) |
| --- | --- | --- |
| фон | `#ffffff` | `#0f172a` |
| поверхность (модалки, инпуты) | `#ffffff` | `#1e293b` |
| текст | `#171717` | `#f1f5f9` |
| вторичный текст | `#737373` | `#94a3b8` |
| разделитель | `#e5e5e5` | `#1e293b` |
| акцент | `#1d4ed8` | `#93c5fd` |
| success / error / warn | `#15803d` / `#b91c1c` / `#a16207` | `#4ade80` / `#f87171` / `#fbbf24` |

**4.5. Стиль.** Ряды списков с тонкими разделителями вместо карточек с тенями; одна primary-кнопка на экран («+ Новый дайджест», «Сохранить»), остальные действия — текстовые кнопки с иконками; статус — цветная точка + слово: `ok` зелёный, `error` красный, `empty` серый, `processing` — янтарный с мягким спиннером (сейчас всё не-`ok` красное). Модалки, логин-страница и «Настройки» приводятся к тому же стилю. `alert()`/`confirm()` заменяются тостами (правый нижний угол, автоскрытие) и confirm-модалкой; подтверждение удаления дайджеста предупреждает: «история его запусков тоже будет удалена».

**4.6. «История».** Панель фильтров над списком: select «Все дайджесты» (из `/api/digests/options`) + select «Все статусы»; смена фильтра сбрасывает на первую страницу. В строке: имя, статус-точка, дата обработки, период, число материалов, индикатор письма (`mail_status=failed` — иконка `i-mail-x` красным с `title=mail_error`; `sent` — ничего; `skipped`/`''` — ничего). «Открыть» запрашивает view-link и открывает вкладку. Пока в видимом списке есть `processing`, страница перезапрашивается каждые 10 с с сохранением фильтров и номера страницы.

**4.7. Пагинатор** (общий компонент в `ui.js`): «← 1 2 3 … N →» с многоточием (окно ±2 от текущей), скрывается при `total ≤ per_page`. Используется в «Дайджестах» и «Истории». `per_page` фиксирован — 20.

## Edge cases

- **`page` за пределами данных** → `items: []`, честный `total`; UI при `page > максимума` (например, после смены фильтра) сбрасывается на 1.
- **Выбранный в фильтре дайджест удалён** → каскад удалил и его запуски; при следующей загрузке опции фильтра обновляются, UI сбрасывает фильтр на «Все дайджесты».
- **Автообновление** не сбрасывает фильтры, страницу и позицию скролла; при уходе со страницы «История» таймер снимается.
- **Подписанная ссылка передана третьему лицу** — работает до истечения `exp` (15 мин); приемлемо, содержимое и так уходит почтой.
- **Редирект картинки на приватный IP** — проверка в `DialContext` выполняется для каждого соединения, включая редиректные.
- **`mail_status` у старых записей** — `''`, UI ничего не показывает.
- **Уменьшили `keep_runs_days`** — ближайшая суточная чистка удалит лишнее вместе с каталогами картинок; ошибки удаления каталогов логируются и не прерывают чистку.
- **Рестарт во время чистки** — операции идемпотентны, следующая чистка доделает.
- **Лимитер логина и память** — записи с истёкшей блокировкой и нулевым счётчиком удаляются при обращениях; на одного пользователя-цель перебора хранится одна запись на IP.
- **Тема при первом заходе** — `system`; вспышки светлого нет благодаря инлайн-скрипту в `<head>`.
- **Переполнение очереди триггеров при создании включенного дайджеста** — дайджест сохраняется (200), отказ очереди логируется; ближайший тик планировщика запустит его сам (у нового дайджеста `next_run_at IS NULL`).
- **Блокировка попапов при открытии просмотра** — «Открыть» открывает вкладку синхронно в обработчике клика (`window.open`) и подставляет URL после ответа `/api/runs/{id}/view-link`, чтобы браузер не счёл вкладку попапом.

## Testing

- **handlers (httptest):** пагинация (`page`/`per_page`, дефолты, границы, 400 на мусор), фильтры `digest_id`/`status` и их комбинация, конверт `{items,total}`, `materials_count`, `/api/digests/options`, view-link (валидная подпись, протухшая, битая, чужой `run_id` → 404), 503 при переполнении очереди, 429 от лимитера логина.
- **images (юнит):** SSRF-guard — приватные/loopback/link-local IP отклоняются, публичные проходят; лимит 10 МБ; отказ по `Content-Type`.
- **auth (юнит):** лимитер — блокировка после 5 неудач, удвоение, сброс при успехе, истечение.
- **scheduler/processor (юнит):** `Trigger` возвращает `false` на полном канале; сброс `processing → error` на старте; `SetRunMail` пишет статус после ретраев (мок SMTP).
- **Смоук UI:** переключение темы (3 состояния, перезагрузка сохраняет), фильтр + пагинация в «Истории», тосты, confirm-модалка, автообновление при `processing`.

## Migration plan

Три фазы, каждая коммитится отдельно и оставляет сервис рабочим:

1. **Надёжность (бэк):** миграция 005, пункты 3.1–3.8. Фронт продолжает работать: старые эндпоинты ещё отдают прежний формат.
2. **API пагинации/фильтров:** конверт `{items,total}`, фильтры, `options`, `materials_count`. Фронт обновляется в этой же фазе минимально (адаптация к конверту), без редизайна.
3. **Фронт-редизайн:** структура модулей, тема, иконки, стили, пагинатор, фильтры, тосты/модалки, автообновление, настройка ретеншена в UI.
