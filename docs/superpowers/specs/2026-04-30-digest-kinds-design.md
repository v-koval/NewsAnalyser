# Digest kinds: news and interesting facts

## Problem

Сейчас все дайджесты обрабатываются как новостной поиск: агент ищет публикации по теме и периоду. Нужен второй сценарий — «Подборка интересных фактов» по теме, где часть материалов привязывается к календарным датам внутри окна составления (день+месяц, без учёта года: дни рождения / смерти деятелей по теме, яркие исторические события), а часть — фактологические заметки по теме без привязки к дате.

Все ранее созданные дайджесты должны остаться новостными без изменения поведения.

## Goal

- Пользователь при создании/редактировании дайджеста выбирает один из двух типов: **«Новостной дайджест»** или **«Подборка интересных фактов»**.
- Для типа `news` поведение системы не меняется.
- Для типа `facts` агент собирает материалы по описанной выше логике; они хранятся, рендерятся в HTML и отправляются по почте теми же механизмами, что и новости.

## Non-goals

- Календарной группировки фактов по датам в письме.
- Меток типа факта («день рождения» / «событие») в карточке.
- Отдельных полей `fact_date` / `fact_kind` в базе.
- Отдельной таблицы под факты или отдельного вьюера запусков.
- Управления количеством фактов или пропорцией «по датам / по теме» из UI — пропорцию выбирает агент.

Эти расширения сейчас не нужны и могут быть добавлены позже точечной миграцией, если понадобятся.

## Design

### Data model

В `digests` добавляется одна колонка:

```sql
-- internal/db/migrations/004_add_digest_kind.sql
ALTER TABLE digests
    ADD COLUMN kind TEXT NOT NULL DEFAULT 'news'
        CHECK (kind IN ('news', 'facts'));
```

`DEFAULT 'news'` автоматически проставляет всем существующим записям тип «Новостной дайджест». `CHECK` страхует от случайных значений в будущем.

Структура `digest_materials` **не меняется**. Колонки `url` и `image_url` остаются как есть; для фактов агент может вернуть пустую строку, она проходит ограничение `NOT NULL` и трактуется кодом как «нет источника / нет иллюстрации».

В Go-модели:

```go
type Digest struct {
    // ... существующие поля
    Kind string `json:"kind"` // "news" | "facts"
}
```

В `repo.scanDigest`, `digestCols`, `CreateDigest`, `UpdateDigest` добавляется поле `kind`. В хендлерах `createDigest` / `updateDigest` нормализация:

- пустая строка (поле отсутствует или передан `""`) → `"news"` — обратная совместимость со старыми клиентами;
- значение из whitelist (`"news"` / `"facts"`) → пропускается;
- любое другое непустое значение → 400 `bad request`.

### Processor

В `processor.Run` после получения `Digest` и периода `from..to` выбирается промпт по `d.Kind`:

```go
var prompt string
switch d.Kind {
case "facts":
    prompt = buildFactsPrompt(d, from, to)
default:
    prompt = buildPrompt(d, from, to)
}
```

Дальше вся последующая логика общая: вызов Cursor-агента, парсинг JSON, сохранение материалов через `AddMaterial`, дозагрузка картинок, рендер HTML, рассылка письма, обновление `last_run_at` / `next_run_at` через `advanceSchedule`.

Структура ответа агента (`materials` + `discovered_sources` + `analyzed_sources`) — одна и та же для обоих типов. Для фактов в `materials` идут факты; в `analyzed_sources` агент возвращает использованные справочные домены (например, `wikipedia.org`).

### Facts prompt

`buildFactsPrompt(d, from, to)`:

1. Объясняет агенту его роль: «формируешь подборку интересных фактов по теме».
2. Передаёт тематику (`d.Topic`) и язык (`d.Language`).
3. Из периода `from..to` (UTC) формирует **явный список календарных пар (день, месяц)**, попадающих в окно — например, «1 мая, 2 мая, 3 мая, 4 мая, 5 мая, 6 мая, 7 мая». Это снимает с агента задачу разбираться с таймзонами и форматами дат. Список строится в Go: проходим от `from.Truncate(24h)` до `to.Truncate(24h)` шагом в сутки и собираем `(day, month)` пары; если окно охватывает 365+ дней — передаём пометку «весь год».
4. Просит подобрать **несколько фактов, привязанных к датам** из списка (день рождения / день смерти известного деятеля по теме, либо яркое событие, произошедшее в эту календарную дату в любом году) **и несколько фактов по теме без привязки к дате**. Конкретное количество и пропорцию агент выбирает сам.
5. Описывает поля материала ровно как в новостном промпте: `url` (можно пустой, если уместного источника нет), `title`, `image_url` (можно пустой), `summary_title`, `summary_text`, `full_text`. Никаких новых полей.
6. Повторяет существующие требования к JSON (RFC 8259, UTF-8, экранирование кавычек, без комментариев и пояснений) и формат ответа `{materials, discovered_sources, analyzed_sources}`.

Существующая логика картинок (`Images.ResolveArticleImage` + `Images.Fetch`) применима без изменений: пустой `url` → `ResolveArticleImage` ничего не найдёт; пустой `image_url` → нет кандидатов; результат — материал без локальной иллюстрации, что корректно обрабатывается шаблоном.

### HTML template

Единственная правка в `buildHTML` — блок «Источник» оборачивается в условие:

```go
if m.URL != "" {
    fmt.Fprintf(&b, `<p class="src">Источник: <a href="%s">%s</a></p>`,
        html.EscapeString(m.URL), html.EscapeString(m.URL))
}
```

Блок иллюстрации уже под условием `if img != ""`, доработок не требует. TOC и якоря работают одинаково для обоих типов. Стили и общая структура страницы — общие.

### Frontend

В `openDigestModal` (`internal/handlers/web/app.js`) добавляется селект типа сразу после «Название»:

```html
<label>Тип дайджеста
  <select name="kind">
    <option value="news">Новостной дайджест</option>
    <option value="facts">Подборка интересных фактов</option>
  </select>
</label>
```

При редактировании выставляется `form.kind.value = d.kind || 'news'`. В payload `POST/PUT /api/digests` добавляется `kind: form.kind.value`. Дефолт `'news'` страхует случай, когда сервер вернул запись без поля.

В `renderDigests` рядом с бейджами «включен / каждые N ч / язык» добавляется бейдж типа:

```js
<span class="badge off">${d.kind === 'facts' ? 'Факты' : 'Новости'}</span>
```

В `renderRuns` ничего не меняется — тип запуска не визуализируется отдельно.

## Edge cases

- **Изменение `kind` в форме редактирования** разрешено и затрагивает только последующие запуски. Прошлые `digest_runs` остаются неизменными — они иммутабельны и хранят свой HTML.
- **Старые клиенты без `kind` в payload**: серверная нормализация ставит `"news"`. Старые ответы API без `kind` фронт трактует как `"news"`.
- **Невалидное непустое значение `kind`**: хендлер возвращает 400 (whitelist `news`/`facts`). Серверный `CHECK` — второй рубеж защиты на случай прямой записи в БД.
- **Первый запуск дайджеста типа `facts`**: период определяется тем же кодом (`now - 7d`, если предыдущих запусков нет). Окно из 7 дней для фактов нормально — агент видит 7 календарных дат.
- **Очень широкое окно** (`frequency_hours` ≥ 365·24): список дат превратился бы в весь год — заменяем его на пометку «весь год» в промпте.

## Testing

- Юнит: построение списка `(day, month)` пар по `from..to` для коротких и длинных окон, переход через год (например, 30 дек — 3 янв).
- Юнит: нормализация `kind` в хендлере (пустая строка → `news`, невалидная → 400).
- Юнит: `buildHTML` с `m.URL == ""` не рендерит блок «Источник».
- Интеграционный (мок Cursor): прогон дайджеста типа `facts` сохраняет материалы и формирует HTML без падений на пустых `url`/`image_url`.
- Smoke-тест UI: создание дайджеста типа `facts`, редактирование, переключение типа, бейдж в списке.

## Migration plan

1. Применить `004_add_digest_kind.sql` — все существующие записи получают `kind = 'news'`.
2. Развернуть бэк с новым полем (нормализация и whitelist в хендлерах, ветвление в процессоре, исправление шаблона).
3. Развернуть фронт с селектом и бейджем.

Порядок 2/3 не критичен: бэк совместим со старым фронтом (нормализация в `news`), фронт совместим со старым бэком (`d.kind || 'news'`).
